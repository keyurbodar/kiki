# How a package plugs in

Read this first. kiki is built as many small packages (one thread, one PR each) running in parallel against one contract on `main`. The contract is the folder layout, the route tree, the primitive APIs and the token names. If your PR keeps to your own directories and keeps those APIs stable, it merges without conflicts.

## Layout

| Layer      | Path                           | One directory per                                               | Owner                                                 |
| ---------- | ------------------------------ | --------------------------------------------------------------- | ----------------------------------------------------- |
| Tokens     | `src/tokens/`                  | layer (primitives, semantic, components, themes, motion, fonts) | KIKI-10 (AMA-36)                                      |
| Primitives | `src/primitives/<name>/`       | Capy `ui/*` primitive                                           | A4, A5, A6, A7                                        |
| Components | `src/components/<name>/`       | Capy `shared/*` composite                                       | the package that first needs it (see parity map §2.2) |
| Features   | `src/features/<group>/<unit>/` | screen group, then unit                                         | the WP named in the group README                      |
| Routes     | `src/routes/`                  | route (TanStack file route)                                     | the WP for that screen                                |
| Data       | `src/data/`                    | API group, mock group                                           | A3 (KIKI-13), A8 (KIKI-14)                            |
| Helpers    | `src/lib/`                     | helper module                                                   | anyone, additive only                                 |

Imports go downward only: routes → features → components → primitives → tokens. `@/` resolves to `src/`.

## Rules that keep PRs conflict-free

1. **Own your files.** Edit only the directories your package owns plus the route files for your screens. If you need a change in another package's directory, make it additive (new export, new optional prop) and say so in the PR body.
2. **Never change a published signature.** Primitive and component stubs already export their final props, variant keys and data-slot names. Fill in internals and class strings; add optional props if you must; never rename or remove.
3. **Shared registries are generated or append-only.**
   - Route tree: `src/routeTree.gen.ts` is generated by the TanStack Router plugin on `bun run dev`/`build`. Never edit it by hand. If two PRs both regenerate it, take main's copy and rebuild.
   - Settings nav: one file per page in `src/features/settings/nav/entries/`, collected by `import.meta.glob`.
   - New registries follow the same pattern: an `entries/` directory plus a glob, never a hand-maintained list.
   - Icon ids are generated from the sprite by the assets package (A1/KIKI-10) under `src/primitives/icon/`.
4. **Tokens only.** No raw px, hex, ms or breakpoints outside `src/tokens/`. Use the CSS variables and the Tailwind utilities generated from them. Until KIKI-10's token PR lands, `src/tokens/contract.css` declares every token name with a placeholder value.
5. **Data through the data layer.** Read and write through the A3 HttpApi client and `MockServices` layers; event payloads come from A8's schemas. Never fetch directly, and never copy capture content into fixtures.
6. **Stack only.** bun, and only dependencies already in `package.json`. Ask Yuzu before adding one.

## Adding a screen

1. Find your route file. Every app route already exists under `src/routes/` with a placeholder, its params, its search params (`validateSearch`) and its redirects.
2. Build the screen in `src/features/<group>/<unit>/`, export it from the unit's `index.ts`.
3. In the route file, swap `RoutePlaceholder` for your feature component. Keep `createFileRoute`'s id, `validateSearch` and `beforeLoad` as they are unless your WP owns that change.

## Filling in a primitive

1. Open `src/primitives/<name>/<name>.tsx`. The cva keys and defaults match Capy's bundle; fill in the class strings with token utilities.
2. Keep every `data-slot` value. Base UI parts are inferred (parity map §4.1.1); if you find a different part is right, swap it without changing the exported names or props.
3. Add tests next to the file.

## Checks

```sh
bun run build && bun run typecheck && bun run lint && bun run test
```

Open the PR against `main` with `tools.pr.create`, rebase yourself when main moves, and let Yuzu merge.
